# ShopFlow Backend — Slice 1: Foundation (Auth, Users, Schema Baseline)

**Date:** 2026-08-11
**Status:** Approved
**Source requirements:** `Software-Requirements.pdf` (SRS, "ShopFlow")
**Reference implementation:** https://github.com/pardeep16/shopEase/tree/master/backend

## 1. Context

The SRS describes a full e-commerce platform: authentication, catalog, inventory,
cart, checkout, coupons, payments, orders, refunds, notifications, admin reporting.
That is far too much for one design document, so the work is decomposed into
sequential slices. Each slice gets its own spec, plan, and implementation cycle.

| Slice | Contents |
|---|---|
| **1. Foundation** (this document) | Schema baseline, config, error handling, auth (JWT + RBAC), users, roles, addresses |
| 2. Catalog & inventory | Product/category CRUD, variants, images, search, filtering, stock |
| 3. Cart & checkout | Cart, coupons, tax/shipping, stock reservation |
| 4. Payments & orders | Gateway integration, webhooks, order lifecycle, refunds |
| 5. Admin & ops | Dashboard, reports, notifications, deployment, monitoring |

### Starting point

An existing Spring Boot project sits in `e-commerce-backend/`. It compiles
(verified: `./mvnw compile` → BUILD SUCCESS) and contains five catalog entities
(`Product`, `Category`, `CategoryType`, `ProductVariant`, `Resource`), a
`ProductMapper`, a `ProductService`, and one endpoint, `GET /api/products/{id}`.
There is no database, no schema management, no security, and no meaningful tests.

### Decisions taken

- **Stack: Spring Boot**, not the NestJS + Prisma named in SRS §6. Both the
  reference repo and the existing code are Spring Boot; the SRS architecture
  section is treated as outdated.
- **Goal: a real store intended for launch.** Correctness of money and stock,
  reproducible schema, and audit logging are therefore requirements, not extras.
- **Primary keys: UUID**, generated by the application. Sequential integer IDs
  would let customers enumerate other users' orders.
- **Package layout: feature packages**, not layer packages. At full SRS scope,
  layer folders become 30-file grab bags with no visible module boundaries.

## 2. Scope of this slice

**Delivered:**

- Flyway schema baseline covering auth, user, and catalog tables
- Registration, login, refresh, logout
- Password reset (token plumbing; logging email implementation)
- JWT authentication and role-based authorization
- Profile and address management
- RFC 7807 error handling, request validation, rate limiting on auth endpoints
- Auth audit logging
- Profile-based configuration with no committed secrets
- OpenAPI documentation
- Repair of the existing catalog module so it actually works

**Explicitly out of scope:** email verification gating login, a real email
provider, Redis, product/category CRUD, search, image upload, cart, orders,
payments, deployment.

## 3. Technology

| Concern | Choice |
|---|---|
| Framework | Spring Boot 4.1.0, Java 17, Maven |
| Database | PostgreSQL 16 (local via Docker Compose) |
| Schema | Flyway, hand-written SQL, `ddl-auto=validate` |
| Persistence | Spring Data JPA / Hibernate |
| Security | Spring Security + JJWT, BCrypt (strength 10) |
| Validation | Jakarta Bean Validation |
| Rate limiting | Bucket4j (in-memory) |
| Docs | springdoc-openapi |
| Tests | JUnit 5, MockMvc, Testcontainers |

`ddl-auto=validate` means Flyway owns the schema and Hibernate only checks that
entities match it. Drift fails at boot rather than in production. Note that
Flyway here is not about migrating existing data — there is none — it is how
tables get created reproducibly on any machine, including the production server.

## 4. Package structure

```
com.mvp.ecommercebackend
├── auth/          AuthController, AuthService, TokenService, RefreshTokenService,
│                  PasswordResetService, entities (User, Role, RefreshToken,
│                  PasswordResetToken, AuthEvent), repositories, dto
├── user/          MeController, AddressController, services, Address entity, dto
├── catalog/       the five existing entities, ProductController/Service/Mapper
├── common/        GlobalExceptionHandler, BaseEntity, custom exceptions
├── config/        SecurityConfig, JwtAuthenticationFilter, JwtProperties,
│                  RateLimitFilter, OpenApiConfig
└── notification/  EmailSender (interface), LoggingEmailSender
```

**Layering rule.** Controllers handle HTTP and validation only. Services hold
business logic and own `@Transactional` boundaries. Repositories do data access.
Entities never cross the controller boundary — controllers expose DTOs only.
Cross-feature access goes through the other feature's service, never its
repository.

## 5. Data model

Flyway `V1__init.sql` creates all tables; `V2__seed_roles.sql` seeds roles and
the initial admin. All primary keys are `uuid`. All tables carry
`created_at` / `updated_at` (`timestamptz`).

### Auth and user tables

**`users`** — `id`, `email` (unique, case-insensitive via a unique index on
`lower(email)`), `password_hash`, `full_name`, `phone`, `status`
(`ACTIVE` / `SUSPENDED`), `email_verified` (boolean, default false).

**`roles`** — `id`, `code` (unique: `CUSTOMER`, `ADMIN`), `name`.

**`user_roles`** — `user_id`, `role_id`, composite primary key.

**`addresses`** — `id`, `user_id` (FK, indexed), `recipient_name`, `phone`,
`line1`, `line2`, `city`, `state`, `postal_code`, `country`,
`is_default_shipping`, `is_default_billing`.

**`refresh_tokens`** — `id`, `user_id` (FK, indexed), `token_hash` (unique),
`expires_at`, `revoked_at` (nullable), `replaced_by` (nullable self-FK),
`user_agent`.

**`password_reset_tokens`** — `id`, `user_id` (FK, indexed), `token_hash`
(unique), `expires_at`, `used_at` (nullable).

**`auth_events`** — `id`, `user_id` (nullable — failed logins may not resolve to
a user), `event_type` (`LOGIN_SUCCESS`, `LOGIN_FAILURE`, `LOGOUT`,
`TOKEN_REFRESH`, `TOKEN_REUSE_DETECTED`, `PASSWORD_RESET_REQUESTED`,
`PASSWORD_RESET_COMPLETED`), `ip_address`, `user_agent`, `created_at`.

Three deliberate choices. Tokens are stored **hashed** (SHA-256), so a database
leak cannot be replayed. `auth_events` exists from the start because retrofitting
an audit trail after an incident is too late. `addresses` lands here rather than
at checkout, since the SRS puts "save addresses" under the Customer role and the
table is trivial now versus a schema change later.

### Catalog tables

`categories`, `category_types`, `products`, `product_variants`,
`product_resources` — matching the five existing entities, with `uuid` keys,
proper foreign keys, and indexes on `products(category_id)`,
`products(category_type_id)`, `product_variants(product_id)`, and
`product_resources(product_id)`.

## 6. Authentication design

### Token model

**Access token** — JWT, HS256, ~15 minute expiry, claims `sub` (user id),
`email`, `roles`, `iat`, `exp`. Verified by signature alone, so no database read
per request.

**Refresh token** — 256 bits from `SecureRandom`, base64url-encoded, returned raw
to the client exactly once and persisted only as a SHA-256 hash. 30-day expiry.

### Refresh rotation with reuse detection

Every `/auth/refresh` call revokes the presented token and issues a new one,
recording `replaced_by` to form a chain. If an **already-revoked** token is
presented, that token leaked and was replayed: the entire token family for that
user is revoked and a `TOKEN_REUSE_DETECTED` event is logged.

This is what makes stored refresh tokens genuinely safer than a long-lived JWT
rather than merely more code.

### Flows

**Register** — validate input, reject duplicate email with 409, hash with BCrypt,
assign `CUSTOMER`, issue a token pair. Registration can never grant `ADMIN`; the
first admin comes from `V2__seed_roles.sql`.

**Login** — verify credentials, issue a pair, log the event. Unknown email and
wrong password return the **same** generic 401, so the endpoint cannot be used to
discover which addresses have accounts. Rate limited.

**Refresh** — rotation and reuse detection as above.

**Logout** — revoke the presented refresh token. The access token stays valid for
its residual lifetime (≤15 min); that is the accepted cost of stateless
verification, bounded by the short expiry.

**Password reset** — `POST /auth/password-reset/request` returns **202 regardless
of whether the email exists**, again to prevent enumeration, and hands a
single-use hashed token (1 hour expiry) to `EmailSender`.
`POST /auth/password-reset/confirm` validates and consumes the token, updates the
password hash, and **revokes every refresh token for that user**, since a reset
implies possible compromise.

### Authorization

`SecurityConfig` uses `SessionCreationPolicy.STATELESS` with a
`JwtAuthenticationFilter` ahead of the username/password filter. CSRF is disabled
because the API is token-based and stateless — no cookie-borne credentials exist
to forge. This satisfies the SRS's "CSRF protection (where applicable)".

| Path | Access |
|---|---|
| `/auth/**` | public |
| `GET /api/products/**`, `GET /api/categories/**` | public |
| `/actuator/health`, `/swagger-ui/**`, `/v3/api-docs/**` | public |
| `/api/admin/**` | `ROLE_ADMIN` |
| everything else | authenticated |

Method-level `@PreAuthorize` is applied as defence in depth, so a controller
added later outside a matched path is not accidentally public.

### Rate limiting

Bucket4j, in-memory, keyed by client IP, on `/auth/login`, `/auth/register`, and
`/auth/password-reset/request`. Exceeding the limit returns 429.

**Known limitation:** in-memory buckets mean limits are per-instance and reset on
restart, which weakens under horizontal scaling. Moving this to Redis is deferred
to the ops slice, and is recorded here so it is not forgotten.

## 7. Error handling

A single `@RestControllerAdvice` returns RFC 7807 `application/problem+json` so
every error shares one shape:

```json
{
  "type": "about:blank",
  "title": "Validation failed",
  "status": 400,
  "detail": "Request contains invalid fields",
  "instance": "/auth/register",
  "errors": [{ "field": "email", "message": "must be a valid email" }]
}
```

| Condition | Status |
|---|---|
| Bean validation failure | 400 |
| Bad or missing credentials, invalid/expired token | 401 |
| Authenticated but insufficient role | 403 |
| `ResourceNotFoundException` | 404 |
| Duplicate email | 409 |
| Rate limit exceeded | 429 |
| Unhandled exception | 500 |

A 500 response carries a generated correlation id and nothing else. Stack traces
and internal messages are logged, never returned.

## 8. Configuration

The current `application.properties` hardcodes `postgres` / `postgres`. That is
removed.

- **`dev` profile** — reads from a gitignored `.env`; `docker-compose.yml`
  provides Postgres 16 locally.
- **`prod` profile** — every secret from environment variables. Startup **fails
  fast** if `JWT_SECRET` is missing or shorter than 32 bytes, rather than booting
  with a weak key.
- Both profiles set `spring.jpa.hibernate.ddl-auto=validate`.

Committed configuration contains no credentials. `.gitignore` covers `target/`,
`.idea/`, `.env`, and `.DS_Store`.

## 9. Catalog repairs

The existing catalog module has three defects that must be fixed for the
application to work:

1. **`ProductMapper.getProductThumbnail`** calls `.toString()` on an `Optional`,
   producing the literal string `"Optional[https://…]"` as the thumbnail — or
   `"Optional.empty"` when a product has no primary image. Fixed to return a
   nullable URL. It also throws `NullPointerException` if any `Resource` has a
   null `isPrimary`; the filter is made null-safe.
2. **No `@GeneratedValue`** on any entity, so every insert would write a null
   primary key. Fixed with generated UUIDs.
3. **`ProductRepository.findAllByCategory(String)`** cannot resolve — `category`
   is a `Category` association, not a `String`. Renamed to
   `findAllByCategoryId(UUID)`.

Additionally the five entities move into the `catalog/` package. No new catalog
features are added in this slice.

## 10. API surface

| Method | Path | Auth | Purpose |
|---|---|---|---|
| POST | `/auth/register` | public | Create account, return token pair |
| POST | `/auth/login` | public | Authenticate, return token pair |
| POST | `/auth/refresh` | public | Rotate refresh token, return new pair |
| POST | `/auth/logout` | authenticated | Revoke refresh token |
| POST | `/auth/password-reset/request` | public | Send reset token (always 202) |
| POST | `/auth/password-reset/confirm` | public | Consume token, set new password |
| GET | `/api/me` | authenticated | Current user profile |
| PATCH | `/api/me` | authenticated | Update name / phone |
| GET | `/api/me/addresses` | authenticated | List own addresses |
| POST | `/api/me/addresses` | authenticated | Create address |
| PATCH | `/api/me/addresses/{id}` | authenticated | Update own address |
| DELETE | `/api/me/addresses/{id}` | authenticated | Delete own address |
| GET | `/api/products/{id}` | public | Product detail (repaired) |

Address endpoints verify ownership, returning 404 rather than 403 for another
user's address so existence is not disclosed. All endpoints are documented via
springdoc at `/swagger-ui`.

## 11. Testing

**Unit tests** — access token generation and validation (valid, expired,
tampered signature, malformed); refresh token hashing, rotation, and reuse
detection; BCrypt verification; password reset token lifecycle including expiry
and single use.

**Integration tests** (Testcontainers, real Postgres):

- Full journey: register → login → access a protected route → refresh → logout →
  refreshing the revoked token fails
- Replaying a rotated refresh token revokes the whole family
- 401 for missing, expired, malformed, and tampered tokens
- 403 when a `CUSTOMER` calls an admin route
- 409 on duplicate registration
- Enumeration safety: identical status and body for known vs unknown email on
  both login failure and password-reset request
- Rate limiting returns 429 past the threshold
- Ownership: user A cannot read or modify user B's address
- Flyway schema validates against the JPA entities (guards against drift)
- `GET /api/products/{id}` returns a real thumbnail URL, not `"Optional[…]"`

## 12. Acceptance criteria

1. `./mvnw verify` passes with all tests green.
2. `docker compose up` then application start yields a fully migrated schema on
   an empty database.
3. A new user can register, log in, read `/api/me`, add an address, refresh, and
   log out.
4. No credentials or secrets appear anywhere in committed files.
5. Starting the `prod` profile without a valid `JWT_SECRET` fails at boot.
6. All endpoints appear in OpenAPI at `/swagger-ui`.
7. Every error response is `application/problem+json`.
8. `GET /api/products/{id}` returns correct data against a seeded product.

## 13. Deferred, with reasons

| Item | Deferred to | Reason |
|---|---|---|
| Redis-backed rate limiting | Ops slice | In-memory is adequate single-instance; becomes wrong under horizontal scaling |
| Real email provider | Notifications slice | Needs provider credentials and domain verification; `EmailSender` interface makes it a config change |
| Email verification gating login | Notifications slice | SRS marks it optional; requires working email delivery first |
| Access token revocation | Ops slice, with Redis | 15-minute expiry bounds the exposure acceptably for now |
| Catalog CRUD, search, images | Slice 2 | Depends on admin authorization from this slice |
